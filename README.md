# 마이리얼트립 여행 큐레이터 (myrealtrip-curator)

기성 리뷰 플랫폼·인플루언서가 아니라, **지극히 개인적인 여행자의 "특별했던 경험"이 묻어나는 글**에서
숨은 명소·맛집을 발굴해 장바구니에 담고, 일정표나 구글 캘린더로 만들고, 그 위에 마이리얼트립 실제
상품을 추천해 연결하는 Codex 플러그인입니다.

## 전체 흐름

5개의 스킬이 파이프라인처럼 이어집니다. 사용자는 스킬 이름을 몰라도 자연어로 요청하면 되고,
**각 단계가 끝나면 플러그인이 먼저 다음 단계를 제안**합니다 — 사용자가 "다음엔 뭘 해야 하지?"를
매번 기억할 필요가 없도록 설계했습니다.

```
discover-local-spots        (여행지·장소유형·테마를 묻고, 개인 여행기에서 숨은 후보 발굴, 마이리얼트립 무관)
        │  "장바구니에 담을 번호를 골라주세요" → 사용자가 번호로 선택
        ▼
manage-travel-cart           (선택한 장소를 로컬 JSON 장바구니에 저장, 마이리얼트립 무관)
        │  "더 담으실 곳 있으세요? 다 담으셨으면 일정표 짜드릴까요?"
        ▼
build-itinerary               (Day별로 배치, 숙소·액티비티 포함 일정표를 Google Sheets로 생성)
        │                                  │
        │ "구글 캘린더에도 등록해드릴까요?"    │ 숙소·액티비티 슬롯
        ▼                                  ▼
sync-google-calendar     recommend-mrt-products  ← 여기서만 마이리얼트립 MCP 호출
   (구글 캘린더 커넥터 사용)      (mcp-servers.myrealtrip.com/mcp)
```

핵심 설계 원칙: **마이리얼트립 MCP는 마지막 상품 추천 한 지점에서만 사용합니다.**
장소 발굴, 장바구니, 일정 조립, 캘린더 등록은 플러그인이 새로 만드는 기능이며 마이리얼트립 앱에
지금 없는 기능이어도 동작합니다.

### 실사용 예시 (처음부터 끝까지)

1. **사용자**: "삿포로 온천 로컬 스팟 찾아줘"
   → `discover-local-spots`가 개인 블로그·현지 유튜버 글에서 후보 6~8개를 **현지어 리뷰 비율**과 함께 제시
2. **사용자**: "1번, 3번 담아줘"
   → `manage-travel-cart`가 장바구니(JSON)에 저장하고, 곧바로 *"다 담으셨으면 일정표 짜드릴까요?"*라고 되물음
3. **사용자**: "응, 3일 일정으로"
   → `build-itinerary`가 (숙소가 미정이면) `recommend-mrt-products`로 인근 숙소부터 추천 →
     장소들을 동네 단위로 묶어 Day별 동선을 짜고 여백 슬롯을 넣어 **Google Sheets**로 생성·공유,
     끝에 *"구글 캘린더에도 등록해드릴까요?"*라고 되물음
4. **사용자**: "응, 등록해줘"
   → `sync-google-calendar`가 실제 캘린더 이벤트로 등록

각 스킬은 이 순서를 몰라도 단독으로도 호출할 수 있습니다 (예: 이미 채워둔 장바구니로 바로
"일정 짜줘"만 요청하면 1~2단계를 건너뛰고 바로 시작합니다).

## 발굴 철학 — 무엇을 소스로 쓰고, 무엇을 배제하는가

이 플러그인의 차별점은 "어디서 찾느냐"에 있습니다. 관광객 쏠림을 재생산하는 소스는 의도적으로 피합니다.

**배제하는 소스**
- Tabelog·대중점평(Dianping) 등 **기성 집계 리뷰 플랫폼** — 상위 노출이 곧 붐빔·관광객화
- **인플루언서, 너무 유명한 블로거, 협찬성 글**

**채택하는 소스**
- 지극히 **개인적인 여행자의 "특별했던 경험"이 묻어나는 글** (개인 블로그·커뮤니티 글)에서
  언급된 명소·맛집. 목적은 **숨은 보석(hidden gem) 발굴**.
- 각 나라에서 **현지인이 실제로 많이 쓰는 검색 사이트·커뮤니티**를 경유해 수집.

**입력 흐름 (`discover-local-spots`가 먼저 묻는 것)**
1. 여행지가 어디인가 (예: 삿포로, 다낭)
2. 가고 싶은 장소 유형 (예: 온천, 스키장)
3. 이번 여행의 테마 (예: 관광, 먹방, 기타(guitar) 구매)

→ 답변에 맞춰 해당 국가에서 주로 쓰는 웹 검색 사이트·커뮤니티를 골라 개인 여행기를 탐색합니다.

**관광객 필터 (핵심 기능)**
- 후보 장소마다 **"현지어 리뷰 비율"** 등의 신호로 관광객 쏠림을 자동 감지합니다.
- 사용자에게 결과를 보여줄 때 **"현지어 리뷰 비율 약 N%"**를 함께 표기해, 얼마나 로컬한 곳인지
  한눈에 판단하게 합니다. (예: `⛩ ○○온천 — 현지어 리뷰 비율 약 82%`)

**커버 우선순위**
- 한국인이 많이 가는 해외 여행지 순으로 커버리지를 넓혀갑니다.
  (예: 일본 → 베트남 → 태국 → … 실제 순위는 최신 통계로 확정 예정)

## 스킬별 동작 방식 — 절차·지식·판단 기준

위 "전체 흐름"이 5개 스킬이 **어떤 순서로** 이어지는지를 보여준다면, 여기서는 각 스킬이
내부적으로 **무엇을 근거로 어떻게 판단**하는지를 정리합니다. 판단 로직 상당수는 SKILL.md
문서가 아니라 `src/tools/`의 파이썬 스크립트에 실제로 구현돼 있습니다.

### 1) discover-local-spots — 숨은 스팟 발굴

**절차**
1. 여행지·장소유형·테마 3가지를 확인한다 (이미 답했으면 다시 묻지 않는다).
2. `spot_searcher.py`를 먼저 실행한다 — 국가별로 설계된 검색 쿼리를 병렬로 돌려 5~15초 안에
   협찬 필터링까지 끝낸다. 지원하지 않는 국가면 국가 설정을 새로 추가하는 것을 우선 검토하고,
   그래도 안 되면 직접 WebSearch(`site:` 한정 검색)로 대체한다.
3. 소스 원칙에 맞는 후보만 6~8개로 추려 정리한다.
4. 후보를 제시하고 장바구니 담기를 유도한다.

**판단 기준 — 소스 원칙**
- **배제**: 기성 집계 리뷰 플랫폼(Tabelog·Dianping·트립어드바이저 등, 국가별 추가 배제 도메인
  보유), 인플루언서·협찬 글, 여러 글에서 복붙된 문구, "N選"/"랭킹"류 집계형 제목, 유쿠리 카이세츠
  형식(합성음성+자막, 현장감 없음) 유튜브
- **채택**: 개인적 서사가 담긴 개인 블로그·커뮤니티 글, 현지인이 실제로 쓰는 사이트를 경유한
  수집, "현지 자국민이 자기 지역을 소개하는 영상"이라는 조건을 모두 만족하는 유튜브만

**협찬 감지 지식 (`spot_searcher.py`)**
- 언어별(한국어·일본어·영어·중국어·베트남어·태국어·프랑스어·이탈리아어·독일어·스페인어) 정규식
  패턴을 따로 관리한다.
- 설계 원칙: "광고", "PR", "제공" 같은 **범용 단어 단독으로는 매칭하지 않는다** — 무관한 문맥에서도
  흔히 등장해 오탐이 많기 때문에, "[협찬]", "이 글은 브랜드로부터 협찬을 받아 작성" 같은
  **명시적 고지 문구만** 매칭 대상으로 삼는다.

**현지어 리뷰 비율 계산 지식 (`review_ratio.py`)**
- 계산 방식: 현지어 리뷰 키워드 검색 히트 수(A) ÷ (A + 한국어[목적지가 한국이면 영어] 검색
  히트 수(B)) × 100. **텍스트 언어 분석이 아니라 "검색 결과 건수 비교"** 방식이다 — 한국어로
  쳤을 때 언급이 적고 현지어로만 많이 나오면 로컬 스팟, 한국어로도 많이 나오면 이미 관광객에게
  알려진 곳으로 판단한다.
- 국가명은 한국어 별칭("로마, 이탈리아")으로도 검색해 실제 한국 블로그·카페 히트를 정확히 잡는다.
- 한계: DDG API가 총 히트 수가 아니라 `max_results`까지만 반환하므로 상한 안에서의 상대 비교다.
  양쪽 언어 모두 상한을 채우는 초유명 관광지는 이 방식으로 잘 구분되지 않지만, 애초에 그런 곳은
  발굴 대상이 아니므로 실사용상 문제는 적다.
- 한계 2: 검색엔진에 Naver·Daum 같은 한국 포털이 없어(아래 "DDG 검색 백엔드" 참고), 네이버
  블로그·카페처럼 외부 크롤러 노출이 제한적인 한국어 콘텐츠는 비교언어(B) 쪽 카운트가 실제보다
  낮게 잡힐 수 있다 — 즉 비율이 실제보다 "더 로컬한 곳"으로 다소 후하게 나올 가능성이 있다.
- 장바구니 항목 전체의 현지어·비교언어 쿼리를 스레드 풀로 한 번에 병렬 검색한다 (항목별 순차
  실행 대비 약 4배 빠름). `--workers`로 동시 실행 개수 조절 가능 (기본 4).

### 2) manage-travel-cart — 장바구니

**절차**: 담기(번호 + 선택적 날짜 파싱) / 보기 / 빼기. 파일은 항상 전체를 읽고 통째로 다시 쓰는
방식으로 수정한다 (부분 수정 명령으로 JSON이 깨지는 것을 방지).

**판단 기준**: 날짜를 같이 말하면 `day` 필드에 즉시 확정 기록하고, 안 말하면 `null`로 두어
`build-itinerary`가 나중에 배치하게 한다. 담을 때마다 "더 담을지, 다 담았으면 일정표를 짤지"를
먼저 물어 사용자가 다음 행동을 고민하지 않게 한다.

### 3) build-itinerary — 일정표 조립

**절차 (6단계)**
1. 사전 확인 — 여행 일수, 숙소 확정 여부, 액티비티 관심 여부
2. 숙소 추천 — 장바구니 장소들의 좌표 무게중심을 계산해 그 동네 인근 숙소를
   `recommend-mrt-products`로 검색 (숙소가 이미 정해져 있으면 건너뜀)
3. 동선 배치 — 동네 단위로 묶어 같은 날에 배치, 이미 `day`가 지정된 항목은 고정하고 `null`만
   자동 배치, 각 Day를 오전→점심→오후→저녁 순으로 정렬, Day당 30분~1시간 여백 슬롯 삽입
4. 액티비티 추천 — 관심 여부와 무관하게 `recommend-mrt-products`를 최소 1회 반드시 호출
5. 시트2 생성 전 필수 확인 — 숙소·액티비티 MRT 링크가 실제로 검색됐는지 재확인 (검색 자체를
   건너뛴 채 링크 없는 표를 만들지 않는다)
6. 스프레드시트 생성·업로드·공유 — `.xlsx` 로컬 생성 → 하이퍼링크 검증 → Google Sheets로 업로드
   변환 → 업로드 후 재검증

**판단 기준**
- 장바구니 장소가 대부분 로컬 스팟이므로 유명 관광지 입장권 추천 우선순위를 낮추고, 하루 일정의
  20~30%는 의도적으로 비운다 (여백 = 우연한 발견의 여지).
- 동선은 "동네를 천천히 걷는" 감각으로 짠다 — 하루에 여러 구를 왔다갔다 하지 않는다.

**동선 계산 지식 (`route_optimizer.py`)**
- 하루 안 순서: 좌표 있는 장소는 **Nearest Neighbor** 방식(가장 이른 시간대 장소에서 출발해
  매번 가장 가까운 다음 장소로 이동)으로 정렬하고, 좌표 없는 장소는 시간대 순으로 뒤에 배치한다.
- Day 배정: `day`가 지정된 항목은 그대로 유지하고, 미지정 항목은 이미 배치된 장소들의 무게중심에
  가장 가까운 날에 배정한다.
- 시간대 추론: 장소 이름·종류의 키워드로 아침/점심/오후(기본값)/저녁/밤 5단계 중 하나로 자동
  분류한다 (예: "카페"·"아침" 포함 → 아침, 시간 무관한 "온천"·"박물관" 등은 기본값인 오후로).

### 4) sync-google-calendar — 캘린더 등록

**절차 (7단계)**: 연결 확인 → 장바구니 상태 확인 → 출발일 확인 → 미리보기 제시 → 중복 확인
(`search_events`) → 확인 후 생성/갱신(`create_event`/`update_event`) → 검증(`batch_read_event`)
→ 완료 안내

**판단 기준 — 이벤트 시간 자동 추론**

| 유형 | 시작 | 종료 |
|------|------|------|
| 카페·아침 | 09:00 | 10:30 |
| 점심·식당 | 12:00 | 13:30 |
| 오후 (기본) | 14:00 | 16:00 |
| 와인바·저녁 | 19:00 | 21:00 |
| 클럽·야시장 | 21:00 | 23:00 |

각 Day 16:30~17:00에는 여백 슬롯 이벤트가 자동으로 추가됩니다.

**정직성 원칙**: 실제 도구 호출 결과가 있을 때만 "등록됐다"고 말한다. 호출 없이 등록됐다고
말하지 않는다.

**대안 경로**: OAuth·플러그인 설치를 원하지 않으면 `ical_exporter.py`로 표준 `.ics`를 만들어
애플 캘린더·Outlook에 수동으로 임포트할 수 있다.

### 5) recommend-mrt-products — 마이리얼트립 연동

이 플러그인에서 마이리얼트립과 **실제로 통신하는 유일한 지점**입니다.

**절차**: MCP 도구 목록을 실시간 확인(버전마다 달라질 수 있어 하드코딩하지 않음) → 예약 필요
항목 판단 → 목적지·장소명·날짜로 검색 → **WebFetch로 링크 접근성 검증**(200이면 그대로 사용,
403/404/5xx면 링크를 클릭 가능한 형태로 내놓지 않고 "직접 검색해보라"고 안내하되 상품 자체는
계속 보여줌) → 1~2개로 추려 제시

**판단 기준**: 유명 관광지·박물관처럼 통상 입장권이 필요한 곳, 사용자가 "투어로 가고 싶다"고
밝힌 곳만 검색 대상으로 삼는다. 도보 산책·개인 식당처럼 예약이 불필요해 보이면 건너뛴다.

**정직성 원칙**: MCP가 실제로 반환한 상품명·가격·링크만 쓴다. 검색 결과가 없으면 "찾지 못했다"고
말하지 지어내지 않는다. 예약·결제는 대신 진행하지 않는다.

### 공통 안전장치 (도구 레벨)

- **DDG 검색 크래시 방어**: DDGS가 쓰는 HTTP 백엔드(primp/reqwest)가 macOS에서 시스템 프록시
  조회 중 SIGABRT로 죽는 경우가 있다. `spot_searcher.py`·`review_ratio.py`·`geocoder.py`
  공통으로 검색 호출을 서브프로세스로 격리해, 죽어도 "결과 없음"으로 넘어가고 전체 실행이
  중단되지 않게 한다. `NO_PROXY=*` 환경변수로 크래시 원인 자체도 우회한다.
- **DDG 검색 백엔드 선정**: `ddgs`가 지원하는 9개 백엔드(bing·brave·duckduckgo·mojeek·
  mullvad_brave·mullvad_google·wikipedia·yahoo·yandex) 중 3개를 제외하고 6개만 쓴다.
  - `duckduckgo`: 요청마다 TLS 설정을 무작위로 바꾸는 봇 탐지 회피 로직이 있는데, 그중
    "TLS 1.3 이상 강제" 옵션이 구버전 OpenSSL/LibreSSL 환경과 충돌해 검색 호출의 60~70%가
    조용히 빈 결과로 처리됐다.
  - `mullvad_brave`·`mullvad_google`: 의존 서비스인 Mullvad의 검색 프록시 **Leta가
    2025-11-27부로 영구 종료**돼 죽은 백엔드로 남아있다 (`ddgs`가 아직 정리 안 함). 즉
    `mullvad_google`이 사실상 유일한 구글 결과 경로였는데 이미 죽어있었다 — 구글 결과가
    꼭 필요하면 공식 Google Custom Search JSON API(무료 키, 일 100건 한도)를 별도로 붙여야
    한다. Bing·Yahoo 등 나머지 6개 백엔드도 대부분 일반 웹을 폭넓게 색인하므로, 이미 어느
    정도 알려진 곳이라면 구글이 없어도 결과가 크게 갈리지 않는다. 다만 저인기·저피링크
    개인 블로그(`discover-local-spots`가 노리는 것)는 색인 규모가 큰 엔진일수록 더 많이
    잡으므로, 구글이 빠진 만큼 놓치는 후보가 있을 수 있다는 한계는 남는다.
  - 나머지 백엔드는 primp(자체 TLS 스택)를 써서 위 TLS 문제가 없다.
- **무관한 검색 결과 필터링**: 위 백엔드 중 일부(특히 `bing`)는 진짜 매칭을 못 찾으면 에러
  대신 완전 무관한 필러 콘텐츠를 반환하는 경우가 있다. `_filter_relevant()`로 결과 제목·본문에
  장소 이름이 실제로 언급됐는지 확인해, 없으면 집계에서 제외한다.
- **다중 백엔드 커버리지 보장**: `ddgs`가 여러 백엔드를 한 번에 조회할 때 동시 조회 엔진 수를
  `min(엔진수, ceil(max_results/10)+1)`로 제한하는데, 이 때문에 `max_results`가 작으면 뒤쪽
  백엔드(결과 품질이 좋은 `yahoo` 포함)가 조용히 호출조차 안 되는 문제가 있었다. 항상 실제
  요청은 `max_results>=60`으로 보내 6개 백엔드를 전부 조회시킨 뒤, 필요한 개수만큼 잘라 쓴다.
- **좌표 확보**: Nominatim(OpenStreetMap, 무료·API 키 불필요)을 우선 쓰고 초당 1건 제한을
  자동 준수한다. 실패하면 DDG 웹검색으로 주소를 추출해 Nominatim으로 재시도한다.
- **링크 검증**: 마이리얼트립 링크(`recommend-mrt-products`)·Google Maps 링크
  (`build-itinerary`)·xlsx→Sheets 변환 후 링크 모두, WebFetch로 실제 접근 가능한지 확인한
  뒤에만 클릭 가능한 링크로 보여준다. 깨진 링크는 숨기되 상품·장소 정보 자체는 계속 보여준다.
